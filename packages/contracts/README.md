# @rgux/contracts

Zod is the single source of truth for the data contracts. Everything under
`schemas/` at the repository root is generated from this package.

```bash
pnpm --filter @rgux/contracts test          # contract, cross-field, and ID tests
pnpm schemas:build                          # regenerate schemas/*.json
pnpm schemas:check                          # fail if the checked-in files drifted
```

## What lives where

| Module | Contents |
| --- | --- |
| `src/evidence-id.ts` | Stable evidence ID construction, parsing, and slugging |
| `src/evidence.ts` | `Evidence` and its ID shape check |
| `src/grounded-text.ts` | `GroundedText`, the unit every factual card field is made of |
| `src/cards.ts` | The five approved cards and the `KnowledgeCard` union |
| `src/actions.ts` | The three approved actions, each with its own payload shape |
| `src/response.ts` | `KnowledgeUIResponse` and its metadata |

## Zod is the gate; JSON Schema is a shape contract

`z.toJSONSchema` **silently drops refinements**. A rule expressed only as a
`.refine` or `.superRefine` disappears from the generated file with no warning
and no error, so a consumer validating with JSON Schema alone gets a weaker
check than the server performs.

Three rules are currently in that gap:

1. `comparisonCard.rows[].values.length === comparisonCard.entities.length` —
   without it a three-entity table validates with two values per row and renders
   misaligned.
2. Card `id` uniqueness within a response.
3. Suggested actions referencing a card that exists in the response.

These are listed in `test/fixtures.ts` as `ZOD_ONLY_FIXTURES`, and
`test/json-schema.test.ts` asserts both halves: Zod rejects each one, and the
generated JSON Schema does not. The gap is therefore enumerated and tested
rather than assumed — if a future Zod release starts emitting one of them, the
test fails and the list gets shorter on purpose.

Referential integrity between `evidenceIds` and the current generation's
retrieval set is deliberately **not** here. It cannot be checked from the
response alone, and it belongs to the M3 validation pipeline.

## Enumerations are derived, never written by hand

`CARD_TYPES` and `ACTION_KINDS` are computed from their unions at runtime.

A hand-written literal array still satisfies `readonly CardType[]` when it is
missing a member, so it goes stale silently the moment a type is added — and any
coverage test built on it keeps passing while the new type bypasses validation
and the renderer. Deriving from `.options` makes that failure mode impossible.
Downstream gates (the M3 output gate, the renderer's component map) must consume
these constants rather than re-listing the types.

## Fixtures

`schemas/__fixtures__/{valid,invalid}` are generated by
`scripts/generate-fixtures.ts` so their evidence IDs are produced by the real
`makeEvidenceId`, not written by hand. Every invalid fixture names the rule it
violates.

Fixture coverage is itself asserted: `contracts.test.ts` derives from
`CARD_TYPES`, `ACTION_KINDS`, and the three grounding modes, and fails when any
of them has no valid fixture. The first version of this package exercised two of
five card types and nothing complained, because nothing was asking.
